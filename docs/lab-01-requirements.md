## 1. Введение

### 1.1. Цель разработки
Создать информационную систему для регистрации, распределения и контроля заявок на ремонт компьютерного и мультимедийного оборудования в компьютерных классах КГЭУ (учебная модель).

### 1.2. Область применения
Система предназначена для использования сотрудниками, администраторами, техническими специалистами и руководителем компьютерных классов. Она автоматизирует процесс обработки заявок от момента создания до закрытия.

### 1.3. Определения и сокращения
- **Заявка (Ticket)** — запись о необходимости ремонта единицы оборудования.
- **Оборудование (Equipment)** — справочник единиц техники (компьютеры, проекторы, интерактивные доски и т.п.).
- **Роль** — набор прав доступа к функциям системы.
- **API** — программный интерфейс для взаимодействия frontend и backend.

---

## 2. Общее описание

### 2.1. Роли пользователей
| Роль | Описание |
|------|----------|
| Сотрудник | Создаёт заявки на ремонт, просматривает свои заявки |
| Администратор | Назначает исполнителя, изменяет статус, отменяет заявки |
| Технический специалист | Выполняет ремонт, меняет статус только назначенных ему заявок |
| Руководитель | Просматривает сводную информацию по всем заявкам |

### 2.2. Окружение
- **Frontend:** Vue 3 (SPA).
- **Backend:** ASP.NET Core Web API.
- **База данных:** PostgreSQL.
- **Аутентификация:** JWT (упрощённая, в рамках семестра).

---

## 3. Функциональные требования

### 3.1. Сотрудник
- **FR-01:** Создание заявки с полями: заголовок (`title`), описание (`description`), оборудование (`equipmentId`).
- **FR-02:** Просмотр списка своих заявок с фильтрацией по статусу.
- **FR-03:** Просмотр деталей своей заявки.

### 3.2. Администратор
- **FR-04:** Просмотр всех заявок.
- **FR-05:** Назначение технического специалиста на заявку.
- **FR-06:** Изменение статуса заявки на любой из допустимых.
- **FR-07:** Отмена заявки (статус `Cancelled`).

### 3.3. Технический специалист
- **FR-08:** Просмотр заявок, назначенных ему.
- **FR-09:** Изменение статуса только своих заявок (например, `InProgress` → `Closed`).
- **FR-10:** Добавление комментария к заявке (опционально).

### 3.4. Руководитель
- **FR-11:** Просмотр сводной статистики: количество заявок по статусам, по оборудованию, по исполнителям.
- **FR-12:** Просмотр отчётов за период.

### 3.5. Общие требования к API
- Базовый путь: `/api/tickets`.
- Методы: GET (список/детали), POST (создание), PATCH (изменение статуса/назначение), DELETE (отмена).
- Аутентификация через JWT-токен.

## 6. Критерии приёмки (Acceptance Criteria)

### US-01 (Создание заявки)
- Поля `title`, `equipmentId`, `description` обязательны.
- После создания заявка получает статус `New` и уникальный номер `number` (например, `REQ-2026-001`).
- Сотрудник видит созданную заявку в своём списке.

### US-02 (Назначение исполнителя)
- Администратор может выбрать техника из списка пользователей с ролью «Технический специалист».
- После назначения заявка получает статус `InProgress` (или остаётся `New` — по согласованию).
- Техник видит назначенную заявку в своём списке.

### US-03 (Смена статуса техником)
- Техник может менять статус только тех заявок, где он назначен исполнителем.
- Допустимые переходы: `InProgress` → `Closed`.
- При попытке изменить чужую заявку возвращается ошибка 403.

### US-04 (Сводка для руководителя)
- Руководитель видит количество заявок в разрезе статусов и по оборудованию.
- Данные доступны только авторизованным пользователям с ролью «Руководитель».

### US-05 (Отмена заявки)
- Администратор может перевести заявку в статус `Cancelled` из любого статуса, кроме `Closed`.
- После отмены заявка не отображается в активных списках.

## 7. Ограничения и допущения

- Система не выполняет физический ремонт, только регистрирует и контролирует заявки.
- Интеграция с 1С, SMS-уведомления, мобильное приложение — вне рамок семестра.
- Объём данных для тестирования — не более 1000 заявок.
